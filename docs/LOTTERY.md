# LOTTERY.md —— 抽奖模式与破洞修补

> 抽奖模式回答的问题：「我不想调参数，直接给我几张好的」。
> 本文说明它的三件套：候选来源、**评分算法**（v2：学习型判别器）、
> 以及把分数最高几张交付出来的机制；外加「破洞修补」后处理的算法细节。

---

## 1. 抽奖模式（条件来源第三项）

```
val 真实条件随机抽 N 条（16~128）→ 每条条件生成 1 张 → 逐张评分 → 交付分数最高的 K 张
```

| 参数 | 范围 | 说明 |
|---|---|---|
| 真实条件抽取数 | 16~128 | 候选数量。128 张在 RTX 2080S 上约 13s（DDIM 50 + 量化） |
| 生成批量 | 16~128 | **逻辑批**：只影响显存占用与进度粒度，不影响结果（见 §1.2） |
| 最终输出（top-K） | 1 ~ min(抽取数, 批量)−1 | 交付的张数，默认 4 |
| 可调项 | 种子 / DDIM 步数 / η / alpha 来源 / 量化 / 破洞修补 | 与其它模式一致 |

### 1.1 三个工程保证

1. **种子决定结果**：初始噪声与 alpha mask 都按「候选序号」一次性预生成
   （`DDPM.sample(x_T=…)` + `generate(alpha_np=…)`），再切成微批送 GPU。
   同 seed + 同候选集 → 同一批候选、同一批 mask、同一名次。
2. **批量不影响结果**：因为 1，批量只决定微批切法。跨批量实测分数差
   ≤0.001（GPU 浮点非确定性，GEMM 形状相关的归约顺序），排序只在极端
   并列处可能互换。
3. **显存自适应**：内部微批 = min(批量, 64, 按空闲显存换算的上限)
   （实测口径：16 张 DDIM100 ≈ 1.2GB → 每张每步 ≈0.00075GB，fp32 保守估）。
   2080S 8GB（可用 ~4GB）上 128 候选实测峰值增量 ~1.25GB。

### 1.2 速度

* 采样套 **fp16 autocast**（`DDPM.sample(amp=True)`，Turing tensor core）：
  2080S 实测 0.24 → **0.10 s/张**（DDIM 50 + 自适应量化，约 2.4×）。
* 服务端 `/api/lottery_estimate` 给出预计耗时；每次抽奖结束后用真实读数
  校准估算常数（指数滑动）。
* 单次权重加载 ~5s（首屏自动 `--preload` 或点生成时载入）。

## 2. 评分算法（v3：池内排名归一的透明融合）

### 2.1 两次失败记录（为什么长成现在这样）

**v1 手搓五组件**：颜色真实度 / 色块结构 / 肢体镜像 / 脸部连贯 / 条件贴合加权。
我们复跑评审时即被否决——色块/脸部/镜像三项**在平涂皮肤上天然满分**（纯色西装 0.947），
细节丰富的设计反而被绝对阈值卡死（精细图 0.695 排不进 top）。
事后特征相关性证实：规则分与色块结构 r=+0.89、与边缘细节 r=−0.26。

**v2 学习型判别器**：真实 vs 生成 CNN（AUC 0.849，防捷径预处理对齐），
评分 = P(real)。再次被我们实测否决——**它与我们的审美判断正交**：同一轮
128 候选里，被判别器打到 0.01~0.10 的恰恰是鲜艳精细的优质设计
（正视图逐张确认），而暗沉平涂霸榜。特征相关性显示其信号与全部可解释
特征近乎零相关（|r|≤0.27），即它学到的是无法解释的「生成分布典型性」，
不是质量。结论：**P(real) 度量的是「像不像这一批生成物的典型样本」，
而我们要的是「出挑的好」——一个尾部统计量，分类器天然给不出来。**

### 2.2 v3 设计

排序只在候选池内做**相对排名**（无绝对阈值），两条正交轴 + 两个硬性保险：

```
total = (0.45 × 丰富度 + 0.55 × 连贯度) × 覆盖率因子 × 退化否决
```

* **丰富度**（排名均值）：设计密度（与主导色距离>60 的可见像素占比）、
  色相熵、饱和度、边缘细节——**正向计分**，直接对齐我们的评审口味；
* **连贯度**（排名均值）：肢体镜像对称、可读脸部（head.front 同时存在
  明暗像素=有眼睛）、覆盖率——噪声/碎屑在这条轴天然垫底；
* **覆盖率因子**：可见率 <30% 线性压分（近空候选）；
* **退化否决**：唯一色 <8（涂色块）×0.3，非有限像素 0 分；
* **判别器 P(real) 只在弹窗展示、不参与排序**（v2 的教训）。

权重常量在 `webui/infer/skin_score.py` 顶部（`W_RICHNESS` / `W_COHERENCE` /
`COVERAGE_LO`），是我们评审反馈的标定值，可按口味调。

### 2.3 验收（与被否决的 v2 同轮复跑：seed=194222 / 128 候选 / DDIM 252 / K32）

| | v2 排名 | v3 排名 |
|---|---|---|
| 我们人工确认过的优质候选（红发角色、蓝金骑士、紫发女孩等，v2 分 0.06~0.18） | 全部沉底（0.01~0.24） | **top-8 占 6 席** |
| 碎屑/近空候选 | 混在中游 | 全部沉底（0.10~0.34） |

对比图：`logs/lottery_scorer/_diag_v3final.png`（正视图 top-8 vs bottom-8）。

> **诚实的边界**：v3 是「我们评审口味的透明规则化」（丰富+连贯），不是客观真理。
> 它偏爱设计感强的候选；若发现某类好图仍被压分，直接调 §2.2 的权重常量，
> 或提交样本重新标定权重。判别器与训练链路保留（`33_train_lottery_scorer.py`），
> 作为弹窗参考读数与未来偏好学习的基础。

## 3. 破洞修补（Hole Healing）

很多皮肤第一层里有**孤立透明像素**（甚至连成一小段），游戏里渲染成
「皮肤破洞」。后处理区开关「破洞修补」默认开启，算法在
`webui/infer/skinheal.py`：

1. 修补范围严格限制在**基础层面的 UV 矩形并集**内——第二层（overlay）的
   留空是合法状态（真实皮肤只有 55~58% 画臂/腿外层），绝不碰；
2. 基础层内找透明像素的 4-连通域，**面积 >20px 整片跳过**（那是合法留白，
   比如未使用的图集区域），避免把结构补坏；
3. 对每个「洞」做**洋葱式填充**：每轮把「至少有一个已填/不透明 8-邻居」的
   洞像素同时填上，颜色取其不透明邻居的平均 RGB，逐层向内推进——
   连续空白由此被平滑地「长」满，而不是糊成一团周长平均色；
4. 8-邻域都找不到颜色源的安全放弃（保持透明），绝不凭空造色。

性能：纯 numpy + 小队列，单张 <1ms。管线位置在**量化之前**
（补进来的颜色跟着进调色板），生成 / 抽奖两条路共用同一份实现。

## 4. 复现 / 重建判别器

```bash
python scripts/33_train_lottery_scorer.py all --n-gen 8000
# generate：生成侧缓存 ~15 分钟（2080S），真实侧预处理 ~3 分钟
# train：   ~5 分钟；结束打印 val AUC 与两侧分数分布
```

发布自带训练好的 `models/lottery_scorer/latest.pt`。**注意：排序完全不依赖
它**（v3 排序只用透明特征），它只作为弹窗里的 P(real) 参考读数与未来
偏好学习的基础；删掉它排序不受影响，仅少一列参考数字。
